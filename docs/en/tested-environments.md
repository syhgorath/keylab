If you hit a problem on Apple Silicon or a newer macOS, please open an issue (with the macOS version, `uname -m` and `bash --version`).

## Packages tried through sshpocket

`linux-hardening 0.12.1` and `utility 0.1.0` (time zone, `LANG` locale, NTP/chrony; Ubuntu 26.04 and Debian 13; tried on real VMs by the package owner with the playbook directly; a real-VM run through the sshpocket menu has not been done yet) are in the lock. With sshpocket 3.6.20 it was tried on real VMs (Ubuntu 26.04.1 and a single-node Proxmox VE 9): the server-type and allowed-network question (when adding a server and on first open), ⛔ when `hardening_ssh_allow_from` is empty, `apply` and a second `preview` (`changed=0`), `hardening_pve_apply` being passed only for that run on Proxmox (and not on Ubuntu), `pve_firewall_*` and the fail2ban settings (`ignoreip` empty + yours, `bantime` 10 min; **an active ban was not tried**). (The 0.9.0 area switches (`hardening_<area>_enabled`) and the permanent-removal actions (`kaldir_onizle`, `kaldir`, `kaldir_geri_yukle`) were tried on real Ubuntu 26.04 and Proxmox VE 9 VMs in earlier rounds; the detailed results below are for 0.8.4; every action tried through sshpocket on the Docker LAB; on real VMs, Ubuntu 26.04 and a single-node Proxmox VE 9, the `audit` → `preview` → `apply` → second `preview` (`changed=0`) cycle was tried, Lynis about 61→83 on Ubuntu and 84 on Proxmox. Also verified on 0.8.4: platform-based menu filtering (`pve_firewall_*` and the Proxmox variables are hidden on Ubuntu), the six per-server switches (`false` writes nothing and does not delete what was already written), the legal banner surviving a reboot on Proxmox, `hardening_pve_web_exclusive` (a same-subnet client that is not on the list can no longer reach 8006 and 3128) and an extra firewall port. **Known limits:** `kernel_modules_disabled` is deliberately refused on Proxmox; `false` does not undo a change that was already applied; **an active fail2ban ban, rejection from an unlisted network, Proxmox with guest VMs/CTs, a Docker VM, Raspberry Pi, an HA cluster and some Ubuntu options (`apt_upgrade`, `restrict_compilers` with a real `gcc`, `auditd_immutable`, `aide_audit_tools`) were not tried**). Usage and the **access-network trap**: [docs/hardening-kullanim.md](../hardening-kullanim.md) (Turkish); standard: [docs/package-standard.md](../package-standard.md).
