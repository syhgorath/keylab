> The rows above (bash, Intel, `--doctor`, `start.command`, fzf menu) describe the **shell era (before 4.0)**; they are kept as history. The current Go version (KeyLab 4.x) targets macOS 27 on Apple Silicon only.

If you hit a problem on Apple Silicon or a newer macOS, please open an issue (with the macOS version and `uname -m`).

## KeyLab app (4.0.x): what was not tried in a real environment

The Go version is verified by automated tests (Go + jsdom; including an update with a real `.app` and `codesign`); macOS 27 on Apple Silicon (arm64) is the only target (the Intel/macOS 15 rows above belong to the shell era). **Not tried in a real environment:** **Quit** on a real USB stick; a real server with a knock sequence (vault knock); a write action's flow on a real VM (modal closing, notification); saving a real passphrase in Keychain mode; **the in-app update from GitHub on a real USB stick** (the exFAT fix arrived in 4.0.13); the pre-action warning window when Python is missing; guest-mode WebKit data cleanup; cleaning leftovers on the next start after Cmd+Q.

## Packages tried through sshpocket

`linux-hardening` and `utility` are in the lock. **`utility` 0.2.0** (merged with the former `kurulum` package: time zone, `LANG` locale, NTP/chrony + `ntp_durum`/`ntp_ayarla` + installing Docker/nginx/MariaDB/Redis; Ubuntu 26.04 and Debian 13) passed on the package owner's Ubuntu 26.04 arm64 **container LAB** (utility 33/33, docker 21/21, native 11/11, preview 8/8, apt 7/7, `run-all`, ShellCheck, `component_validate --strict`). ⚠️ **Not tried:** the merged package on a real VM; `ntp_durum`/`ntp_ayarla` on a real server; chrony together with systemd-timesyncd (Ubuntu 26.04; `ntp_ayarla` does not disable timesyncd); the install actions on Debian 13; write NTP actions are deliberately refused on Proxmox. The earlier `utility 0.1.0` was tried on real VMs only by the package owner with the playbook directly; a real-VM run through the sshpocket menu has not been done yet. With sshpocket 3.6.20 it was tried on real VMs (Ubuntu 26.04.1 and a single-node Proxmox VE 9): the server-type and allowed-network question (when adding a server and on first open), ⛔ when `hardening_ssh_allow_from` is empty, `apply` and a second `preview` (`changed=0`), `hardening_pve_apply` being passed only for that run on Proxmox (and not on Ubuntu), `pve_firewall_*` and the fail2ban settings (`ignoreip` empty + yours, `bantime` 10 min; **an active ban was not tried**). (The 0.9.0 area switches (`hardening_<area>_enabled`) and the permanent-removal actions (`kaldir_onizle`, `kaldir`, `kaldir_geri_yukle`) were tried on real Ubuntu 26.04 and Proxmox VE 9 VMs in earlier rounds; the detailed results below are for 0.8.4; every action tried through sshpocket on the Docker LAB; on real VMs, Ubuntu 26.04 and a single-node Proxmox VE 9, the `audit` → `preview` → `apply` → second `preview` (`changed=0`) cycle was tried, Lynis about 61→83 on Ubuntu and 84 on Proxmox. Also verified on 0.8.4: platform-based menu filtering (`pve_firewall_*` and the Proxmox variables are hidden on Ubuntu), the six per-server switches (`false` writes nothing and does not delete what was already written), the legal banner surviving a reboot on Proxmox, `hardening_pve_web_exclusive` (a same-subnet client that is not on the list can no longer reach 8006 and 3128) and an extra firewall port. **Known limits:** `kernel_modules_disabled` is deliberately refused on Proxmox; `false` does not undo a change that was already applied; **an active fail2ban ban, rejection from an unlisted network, Proxmox with guest VMs/CTs, a Docker VM, Raspberry Pi, an HA cluster and some Ubuntu options (`apt_upgrade`, `restrict_compilers` with a real `gcc`, `auditd_immutable`, `aide_audit_tools`) were not tried**). Usage and the **access-network trap**: [docs/hardening-kullanim.md](../hardening-kullanim.md) (Turkish); standard: [docs/package-standard.md](../package-standard.md).
